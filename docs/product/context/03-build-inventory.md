CONNECTOR MECHANISM, PRECISELY (vkv/backends/voice_kv_connector.py, 574 lines). Decide-what-to-store: every scheduled new request whose block-aligned computed prompt length exceeds what its longest matching stored entry covers gets a store of prompt[0:store_tokens] (store_tokens = min(align(len(prompt)), floor((num_computed+num_scheduled)/block)*block)); entry_id = f'{request_id}:{store_tokens}'. Decide-what-to-load: get_num_new_matched_tokens hashes the request's prompt into a blake2b chain (16-byte digests, one per block, seeded 'voicekv-root', each digest = blake2b(prev_digest || str(token_list_of_block))), walks the index until first miss, returns (matched - num_computed_tokens, False). Decide-what-to-evict from CPU slab: (a) eagerly evict the entry the request matched when the new store extends it ('previous turn's entry is now a strict prefix'); (b) LRU by scheduler tick when used_tokens + needed > 0.90 * capacity_tokens, never evicting entries touched in the current step. Decide-what-to-pin in HBM (arm D only): request_finished reads kv_transfer_params.idle_ms (client-computed = max(0, TTS playback remainder - generation time at 45 tok/s) + 400 ms median gap + 2500 ms median utterance + 150 ms STT final); if idle_ms <= 25,000 ms and the 10 GB pin budget allows, return True so vLLM does not free the blocks; hold = idle_ms*1.3 + 2000 ms; worker get_finished releases after the deadline. No pin => blocks go straight back to vLLM's evictable pool; nothing in the connector proactively evicts from HBM. Restore path: scheduler puts _LoadSpec(entry_id, tok_start=matched-external, tok_end=matched, block_ids) in metadata; worker start_load_kv: if the entry's save event hasn't completed, event.synchronize(); one H2D copy of slab[offset+lo:offset+hi] ([T, L, W] fp16, L=layers, W=2*heads*head_dim) on a side stream, stream.synchronize(); build slot tensor from block_ids; for each layer flat = kv.reshape(2, num_blocks*block_size, -1); flat[:, slots] = staging[:, li].reshape(T, 2, -1).permute(1, 0, 2); then current_stream().synchronize(). Save path: save_kv_layer (called by vLLM per layer during forward) gathers flat[:, slots] for each pending store into a GPU staging tensor [num_tokens, L, W]; wait_for_save allocates slab space (first-fit; fallback standalone pinned tensor), dst.copy_(staging, non_blocking=True) on the side stream after wait_stream(current), records a CUDA event; bind_connector_metadata on later steps reaps finished events and drops staging; staging is capped at 1e9 bytes with synchronous drain of the oldest saves when exceeded. Bytes/token derived from model config: 2 * n_layers * n_kv_heads * head_size * 2 (Qwen2.5-7B: 28*4*128*2*2 = 57,344 B/token; a ~2.5k-token session ≈ 143 MB; 60 GB pool ≈ 1.05M tokens ≈ ~420 such sessions).

HOW THE FOUR ARMS ACTUALLY DIFFER ON GPU (vkv/run.py + evals/modal_arm_a.py): A = plain vLLM with prefix caching. B = same server + VoiceKVConnector (or LMCacheConnectorV1) — purely server-side; the harness's TieringController offload/fetch hooks are inert because KvStore never sees real KV. C = B + client fires a 1-token max_tokens completion of the session's full history at VAD_START (governor-capped by history_tokens*57,344 bytes, 4 GiB in-flight cap, one per session), so 'prefetch' is a full extra request through vLLM's scheduler. D = B + every request carries kv_transfer_params.idle_ms; the connector pins short-idle sessions' blocks. VAD/endpoint hints are only consumed by arm C; FINDINGS.md §3.6 states VAD/endpointing 'contributed nothing measurable in any arm' and that arm D's signal is response length + turn-taking medians.

REUSABILITY SUMMARY. For a production 'session-aware inference' product: the connector is a compact, GPU-validated (per committed runs) reference for content-addressed session-granular CPU-RAM KV tiering with contiguous transfers, async saves with backpressure, and hint-driven residency pinning through the stock KVConnector API — reusable as design + starting code, not as a shippable component (TP=1, fp16 only, non-MLA, prompt-KV only, sync loads, vLLM 0.9.2-pinned, shared-prefix eviction interaction, untested outside Modal). The arm D protocol (client sends predicted idle window per request; server pins accordingly) is the one mechanism that moved the recorded knee and is the most directly reusable idea; its implementation is ~40 lines in the connector plus a 6-line client hint function. For a general benchmark harness: traces (schema/distributions/generator), orchestrator (turn-taking state machine with barge-in/spurious-VAD), loadgen (N-slot semaphore + arrivals), metrics (JSONL events, manifest, analyzer with warmup discard and p95 gate), run/sweep (knee search, evidence_grade flag), VllmHttpEngine (exact-token synthetic prompts, streaming TTFT/ITL, 512-thread pool), Modal sweep driver (per-point container, resumable, infra-vs-run failure distinction), and make_figures (figures purely from raw logs) together form a working multi-turn session load harness (~2,000 lines) that ran ~287k turns on GPU. Generalizing it beyond voice-KV would require: text prompts + tokenizer + chat endpoint, aiohttp with mid-stream abort, server-metrics scraping into events.jsonl, connector/config provenance in manifests, multi-seed aggregation, and removal or parameterization of the voice-specific mocks and the sim-only KvStore plumbing that currently runs (inertly) in GPU mode.

### Gaps (what a production inference provider would still need)

- Connector (voice_kv_connector.py) scope: TP=1 only; fp16/bf16 only (dtype_size hardcoded 2); non-MLA paged layout only; saves only block-aligned PROMPT KV (decode-token KV never saved, and the client resubmits synthetic assistant tokens so decode KV could not be reused in any arm); loads are synchronous inside the scheduler step with no layer-pipelined H2D overlap (README's 'non-negotiable' step 4 not done); no NVMe/disk tier; no cross-node/remote tier; no request-less prefetch (API cannot express it); no proactive HBM free at assistant turn end (RESULTS.md Phase 2 conclusion proposed it; the built connector returns request_finished=False by default and only DELAYS free for arm D pins); eviction = LRU-by-tick + eager eviction of the matched predecessor entry + pin; pinned to vLLM 0.9.2 KVConnectorBase_V1 and vLLM 0.9.2's batched CachedRequestData shape.
- Code-reading observation not documented in repo: because a store evicts the entry it matched, sessions sharing a common prefix (traces use 5 customer system prompts across up to 300 sessions) evict each other's slab entries every turn; effective pool is one entry per prefix lineage, not per session. Impact on the recorded 35–52% hit rates is unquantified.

### Gaps (what a production inference provider would still need)

- Streaming: gateway/app.py:127 hard-sets stream=False; sessions/backend.py and edge SessionDO forward non-streaming with max_tokens=16 hard-coded; no SSE passthrough anywhere.
- Billing/payments: no Stripe/invoicing/card flow; only a $5 signup credit ledger and a 402 when it hits zero; edge hasCredit() fails open on DB errors (index.ts:43); no usage export.
- Auth: no OAuth callback implemented (signup accepts provider/subject as trusted JSON); control-plane management endpoints authenticate with the inference API key, no user session/JWT; no RBAC, audit log, retention/TTL, or encryption-at-rest code despite README 'Governance primitives (v1)' (grep for rbac/audit/prometheus/retention across src/, dexa_platform/, edge/src returns only pricing.py comments).
- Tensor parallelism: src/dexa/engine/vllm_connector.py has zero handling of TP>1 / KV-head sharding (no tensor_parallel references); validated only at TP=1, single attention backend, same GPU arch.
- Chunked prefill in the connector: build_connector_meta only scans scheduler_output.scheduled_new_reqs; vllm_connector.py:608 'TODO: scan cached reqs' - long prompts prefilled over multiple steps are never saved (docs/RESULTS.md: 16k run saved nothing without a max_num_batched_tokens workaround).
- Prefix/block-hash keying: connector keys KV by hash of the whole prompt, so shared-prefix traffic gets zero hits (vllm bench serve prefix_repetition: dexa 3355 ms mean TTFT vs 610 ms no-cache baseline vs 183 ms in-GPU prefix cache); saves are unconditional for every completed prompt (throughput cost).
- NVMe tier enforcement: dexa_platform/sessions/tiering.py and edge/src/tiering.ts only compute an advisory tier label stored on the session record; nothing demotes/evicts/pins KV in LMCache or vLLM; serve/vllm_lmcache_backend.py configures only a 40 GB CPU tier (no LMCACHE_LOCAL_DISK); edge/README.md:88 states the policy is advisory.
- Warm/cold observation: both Python (backend.py:44,60) and TS (session.ts:116) set warm = not first_touch; nothing reads LMCache hit counts or TTFT to confirm a restore actually happened; savings are modeled from a static Qwen2.5-7B/A100 PROFILE table, not measured per request.
- Session-to-replica routing: a single GPU_BACKEND_URL / DEXA_SESSION_BACKEND; no session->replica affinity map, no multi-replica scheduler, no KV migration between replicas, no capacity/admission control for resident sessions.
- Durable session state: Python SessionStore (sessions/store.py) is an in-process dict; Redis not implemented; the Postgres `sessions` table in edge/schema.sql is never written by any code; gateway usage Store and key cache are per-process.
- Tenant isolation of KV: connector store key = model name + prompt hash with no tenant/org component; LMCache backend has no per-tenant namespacing.
